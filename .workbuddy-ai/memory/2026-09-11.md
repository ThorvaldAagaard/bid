but the learning methodology has a structural flaw. Key measured evidence:

## Findings
1. **Advertised method != operating method.** README headline claims
   "PIDM teacher -> ID3 distillation". But `flywheel.py` does NOT import
   `learner.py`. ID3 is reachable only via legacy `main.py`/`invention.py`/
   `pipeline.py`. The real loop = hand-authored patch families + numeric
   `tighten`/`loosen` hill-climb. PIDM appears once in flywheel at
   sample_size=2, max_iterations=6, timeout 0.06 s.
2. **Anchor ledger is flat** — v25/26/27 identical (-19.81 / 4.074 / 53.7).
   By the project's own README criterion this means seed-fitting.
3. **Regret is a high-variance metric.** IMP loss/board spans only 2.66–4.63
   while regret spans +23 to -174 (dominated by slam swings, e.g. -910 on one
   board). Screening on 24-deal tiers chases noise. Prefer IMP loss.
4. **Mirror self-play ceiling** — both sides share one system, so adaptive
   effects cancel (author's own status.md §4.5 / §6.6). Need a heterogeneous
   fixed opponent panel (SAYC / Precision / 2/1 / GIB).
5. **`applied` ledger mixes gated and manual entries.** `flywheel.py` has
   MIN_PATCH_DELTA=0.5, but the `improve_*.py` experiment scripts write to the
   same `flywheel_state.json` with `manual:*` sigs at negative delta (-22.8,
   -22.7, -9.6, -3.0) and repeated `SUPPORT` at delta 0.0. Version history is
   not a clean record of measured improvement.
6. **Student is mis-scaled**: 5.0M params on ~1.5k traces. Loss plateaus
   0.62–0.65, non-monotonic late. Best 70.6% bid acc (2026-08-27, vocab 1458)
   -> 59.8% now (vocab 404; vocab collapse unexplained).
7. **Loop is stalled**: `continuous_state.json` cycle 2, last written
   2026-09-05; last commit 2026-09-06.

## ID3 speedup learning — root cause of it being dead code
`learner.py` was unreferenced by the loops, but it ALSO could not have worked:
`DecisionNet.export_dsl` writes only a depth-1 sketch of an attached classifier
(SPLIT_FEATURE/THRESHOLD/IF) and `load_decision_net_dsl` reads only
`RESOLVED_CALL`, so an attached ID3 tree is destroyed by every save->load cycle
(`intersection_nodes` comes back empty, phi(s) re-widens). Proven with a probe.

Fix: `id3_leaf_paths()` + `id3_tree_to_rules()` in learner.py compile the tree
into ordinary DecisionNetRules. Each leaf path = (all conditions of every rule
in the intersection key) + (path thresholds). ANDing the intersection's
conditions keeps the split from firing in auctions it never saw. No new DSL
syntax -> the hand-ported JS engine stays in sync.
Wired as flywheel `--id3` / `Flywheel(id3=True)` -> `build_id3_patches()`;
states come from `self.train_deals` (seeded) not `Deal.random_deal`.

Bugs I introduced and fixed (regression-tested):
1. base_id was `'_'.join(key)[:20]` -> distinct intersections collided onto one
   rule id; now `ID3_{stem24}_{sha1(key)[:6]}`.
2. `add_rules()` computed `existing` once before the loop -> duplicate ids
   within one batch were all inserted; now updated as it adds.
3. `by_id` lookup is ambiguous for reused rule ids -> now skips intersections
   containing an id with >1 variant.

Measured: ID3 emits 8 rules (78 -> 86) but is net-NEGATIVE on held-out 24
boards (h2h -10.2 -> -14.0, imp_loss 6.68 -> 6.94). Likely data-starved:
~20 ambiguous states means trees fit on 1-3 examples. Delta is within the
~3 pt/bd noise floor. Gate correctly rejects it. Needs hundreds of labeled
states to be useful.

## ID3 persistence — FIXED (tree serialization)
Export now writes a full indented TREE block; loader (`eval_vs_dds.parse_id3_tree`)
and `web/bid_dsl.js` both parse it (same indentation grammar). JS registers the
tree into the existing `net.refinements` hook, so `bid_net.js` needed no change.
Format:
```
INTERSECTION R_1H ^ R_1NT:
  TREE:
    SPLIT hcp <= 16.5 fallback 1H
      LEAF 1H
      LEAF 1NT
```
`fallback` = node majority, mirrors ID3Node.predict on a missing feature
(without it JS went right arbitrarily -> parity bug caught by the JS test).

**Attach, don't compile.** `--id3` now ATTACHES trees (exact: fires only when
matched set == intersection key). Compiling to rules ANDs the key rules'
conditions = a SUPERSET, so it over-fires. Measured (24 boards, seed 7, panel,
both seats): no-ID3 h2h -10.2 / imp 6.68; compiled -14.0 / 6.94;
**attached +0.1 / 6.89**. ~14 pts/bd better than compiling. Mixed: h2h +10.3
but imp_loss +0.21 (different questions: beating opponent vs matching par).
Fixture tests/fixtures/id3_tree.dsl shared by Python + JS tests.

Test counts: 214 python, 387 web engine checks, 12 web id3 parity checks.

## Parallel evaluation (`--jobs`) — added, measured 2.2x
`evaluate_system(jobs=N)` + `_eval_chunk` + `_evaluate_system_parallel` in
eval_vs_dds.py; `--jobs` on flywheel and eval_vs_dds. Everything picklable
(DecisionNet 15KB, panel 5KB, PIDMEngine, BiddingArena).

**MUST use spawn, not fork** — forking after `precompute()` has initialised
native DDS deadlocks inside libdds (hung 10 min in testing). Spawn costs
~2.5s/worker (re-import + DDS init) on EVERY call, so:
- MIN_BOARDS_PER_WORKER = 8; below that, falls back to serial (result reports
  `jobs_used` so it's visible).
- Measured: 96 deals serial 60.5s -> parallel x8 27.7s = 2.19x. 24 deals: 2.13x.
- Serial vs parallel numbers are NOT comparable (serial consumes one RNG in
  board order; parallel seeds per chunk `seed*7919+offset`). Within a parallel
  run it IS reproducible and paired (verified: scores lists identical).
- Set `os.environ.setdefault("PYTHONHASHSEED","0")` before the pool so spawned
  children are deterministic.

Gotcha that cost time: a test script calling evaluate_system(jobs=N) MUST have
an `if __name__ == "__main__"` guard, else spawn re-imports __main__ and each
child re-runs precompute + spawns its own pool -> BrokenProcessPool/recursion.

  OVERCALLS        +2        +0.0000 se 0.000  EXACT ZERO

WHY (the important part) — NOT "guards never match":
N/S seats only (candidate plays N/S; E/W is the frozen panel):
  BALANCING 51 matched / 46 novel; NT_SAFETY 288/283; OVERCALLS 134/63;
  SUPPORT 253/215.
Rules fire constantly and usually add a call NOT already in phi(s) — yet 3
families never change a single outcome.

ROOT CAUSE: arena.play_board calls self.engine.decide (PIDM), which takes
phi(s) from the DecisionNet and SEARCHES to pick the argmax. The DecisionNet is
a CANDIDATE GENERATOR, not a decision procedure. Editing rules only matters
when it changes PIDM's argmax.

=> More fundamental than the noise problem: even with unlimited boards,
patching candidate generation has a small ceiling because search discards most
proposals. TWO INDEPENDENT problems: screen can't SEE a 0.03 effect (§6.16),
and the effect IS ~0.03 because search overrides rules (§6.19).

IMPLICATION: leverage is in the SEARCH (objective, world model, features it
scores on), or in rules derived from what PIDM actually chooses — NOT more
hand-authored candidate rules. Roadmap item 1b rewritten.

Caveat: measured on champion (recommended base). Families were authored against
improved_system.dsl's gaps, so may differ there.

## Bug found+fixed: --jobs silently changed the SEARCH being evaluated
The serial evaluate_system path uses the `arena` it is handed, but the parallel
worker `_eval_chunk` HARDCODED PIDMEngine(sample_size=2, max_iterations=6,
timeout_sec=0.06, max_lookahead_depth=1). So enabling --jobs swapped in a
different search. Nobody noticed because Flywheel's own arena uses exactly the
default config, so numbers were identical for the default path — a latent trap
for any caller with a non-default engine.

Fix: `_evaluate_system_parallel` now takes `arena`, extracts scalar search
config (sample_size, max_iterations, timeout_sec, max_lookahead_depth) and
passes it in the payload; `_eval_chunk` builds its engine from it. Payload grew
10 -> 11 elements; unpacking tolerates the old 10-tuple (falls back to defaults).
Tests: TestParallelHonoursSearchConfig in tests/test_panel_and_imp_metric.py
(3 tests) — uses empty deal lists so no DDS needed, and monkeypatches
